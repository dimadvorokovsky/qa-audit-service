\# Test Cases — Web Application



\## TC-001 — Успешное открытие главной страницы



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Есть интернет-соединение.

\- URL приложения доступен.



\*\*Steps:\*\*

1\. Открыть браузер.

2\. Перейти на главную страницу приложения.



\*\*Expected Result:\*\*

\- Страница успешно открывается.

\- HTTP status code — 200.

\- Основной контент отображается.

\- Критических ошибок загрузки нет.





\## TC-002 — Проверка перехода по внутренней ссылке



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Главная страница открыта.

\- На странице есть внутренняя ссылка.



\*\*Steps:\*\*

1\. Найти внутреннюю ссылку.

2\. Нажать на неё.

3\. Дождаться загрузки страницы.



\*\*Expected Result:\*\*

\- Открывается ожидаемая страница.

\- URL соответствует выбранному разделу.

\- HTTP status code не содержит ошибку 4xx/5xx.





\## TC-003 — Проверка битой внутренней ссылки



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\*\*Steps:\*\*

1\. Получить URL ссылки.

2\. Отправить HTTP-запрос на URL.

3\. Зафиксировать status code.



\*\*Expected Result:\*\*

\- Ссылка ведёт на существующую страницу.

\## TC-004 — Отправка формы с валидными данными



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Страница с формой открыта.

\- Все обязательные поля доступны.



\*\*Steps:\*\*

1\. Заполнить обязательные поля валидными данными.

2\. Заполнить необязательные поля, если требуется.

3\. Нажать кнопку отправки.



\*\*Expected Result:\*\*

\- Форма успешно отправляется.

\- Пользователь получает подтверждение успешной операции.

\- Данные передаются в ожидаемом формате.

\- Ошибки валидации отсутствуют.





\## TC-005 — Отправка пустой формы



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Страница с формой открыта.



\*\*Steps:\*\*

1\. Не заполнять поля формы.

2\. Нажать кнопку отправки.



\*\*Expected Result:\*\*

\- Форма не отправляется, если обязательные поля не заполнены.

\- Для обязательных полей отображаются сообщения валидации.

\- Интерфейс не ломается.

\## TC-007 — Проверка максимальной длины текстового поля

\## TC-013 — Успешный GET-запрос REST API



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Известен рабочий API endpoint.

\- API доступен.



\*\*Steps:\*\*

1\. Отправить GET-запрос через Postman.

2\. Зафиксировать status code.

3\. Проверить response body.

4\. Проверить response headers.



\*\*Expected Result:\*\*

\- Возвращается ожидаемый успешный status code.

\- Response body соответствует контракту.

\- Content-Type соответствует формату ответа.

\- Обязательные поля присутствуют.





\## TC-014 — GET-запрос с несуществующим ID



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- API поддерживает получение сущности по ID.



\*\*Steps:\*\*

1\. Указать заведомо несуществующий ID.

2\. Отправить GET-запрос.



\*\*Expected Result:\*\*

\- API возвращает ожидаемый error status code согласно спецификации.

\- Ответ содержит понятное сообщение об ошибке.

\- В ответе отсутствует внутренний stack trace.





\## TC-015 — POST-запрос без обязательного поля



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Известен POST endpoint.

\- Известна структура request body.



\*\*Steps:\*\*

1\. Сформировать валидный request body.

2\. Удалить одно обязательное поле.

3\. Отправить POST-запрос.



\*\*Expected Result:\*\*

\- Сервер отклоняет некорректный запрос.

\- Возвращается status code согласно API-контракту.

\- Response содержит информацию о причине ошибки.





\## TC-016 — POST-запрос с невалидным типом данных



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\*\*Expected Result:\*\*

\- Сервер корректно валидирует данные.

\- Некорректная сущность не создаётся.

\- Возвращается ожидаемый error response.

\## TC-020 — Проверка Network при основном пользовательском сценарии



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Страница приложения открыта.

\- DevTools открыт.



\*\*Steps:\*\*

1\. Перейти во вкладку Network.

2\. Очистить список запросов.

3\. Выполнить основной пользовательский сценарий.

4\. Проанализировать сетевые запросы.



\*\*Expected Result:\*\*

\- Неожиданные 4xx/5xx отсутствуют.

\## TC-021 — Проверка работы приложения при медленном соединении



\*\*Priority:\*\* Medium



\*\*Preconditions:\*\*

\- Страница приложения доступна.

\- DevTools открыт.



\*\*Steps:\*\*

1\. В Network включить throttling.

2\. Выбрать медленное соединение.

3\. Перезагрузить страницу.

4\. Выполнить основной сценарий.



\*\*Expected Result:\*\*

\- Пользователь видит состояние загрузки.

\- Интерфейс не зависает.

\- После получения ответа данные отображаются корректно.

\- Ошибка timeout обрабатывается понятным способом.

\## TC-023 — Регрессионная проверка исправленного дефекта



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Разработчик сообщил об исправлении дефекта.

\- Доступна версия с исправлением.



\*\*Steps:\*\*

1\. Выполнить исходные Steps to Reproduce дефекта.

2\. Проверить фактический результат.

3\. Проверить связанную функциональность.

4\. Выполнить основной пользовательский сценарий.



\*\*Expected Result:\*\*

\- Исходный дефект больше не воспроизводится.

\- Связанная функциональность не сломана.

\- Новые критические ошибки отсутствуют.





\## TC-024 — Проверка обработки ошибки сервера



\*\*Priority:\*\* High



\*\*Preconditions:\*\*

\- Есть возможность получить или эмулировать ошибку сервера.



\*\*Steps:\*\*

1\. Выполнить действие, вызывающее запрос к backend.

2\. Получить ошибочный ответ сервера.

3\. Проверить UI.



\*\*Expected Result:\*\*

\- Пользователь получает понятное сообщение.

\- Интерфейс не зависает.

\- Система не отображает технический stack trace.

\- Пользователь может повторить действие или продолжить работу.





\## TC-025 — Проверка повторной загрузки страницы



\*\*Priority:\*\* Medium



\*\*Preconditions:\*\*

\*\*Steps:\*\*

1\. Обновить страницу через браузер.

2\. Дождаться окончания загрузки.



\*\*Expected Result:\*\*

\- Открывается та же ожидаемая страница.
